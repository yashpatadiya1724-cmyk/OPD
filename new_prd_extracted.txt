1. Executive Summary
Outpatient Departments (OPDs) in most hospitals and clinics still rely on physical queues, paper tokens, or shouted names to manage patient flow. This creates crowded waiting rooms, unpredictable wait times, poor visibility for patients, and inefficient staff coordination. Patients often arrive early and wait for hours in a physically packed space, which is not only uncomfortable but also a genuine health risk during infectious-disease seasons.
The Hospital OPD Queue Tracker & Dynamic Token System is a real-time platform that digitizes the token issuance and queue management process, built as three connected apps on one Firebase backend: a Patient Flutter app, a Doctor Flutter app, and a React Admin/Reception web panel. Patients receive a digital token upon registration and can track their live position and estimated wait time from their own phone, without needing to be physically present in the waiting area. Reception staff and doctors get a live operational view to call, skip, pause, or complete tokens, with every change reflected instantly on all connected devices.
The system is built entirely on Firebase, which allows the team to ship a fully functional, real-time, multi-user application within a hackathon timeframe without writing or hosting a traditional backend server. Firestore's real-time listeners replace the need for custom WebSocket infrastructure, Firebase Authentication handles staff and patient identity, and Cloud Functions handle server-side business logic such as queue recalculation and notification triggers.
Why This Problem Matters
Reduces physical crowding in hospital waiting areas, which directly improves infection control.
Gives patients control and transparency over their own wait time instead of anxious uncertainty.
Reduces the operational load on reception staff who currently manage queues manually or on paper.
Demonstrates a clean, real-world, sellable use of Firebase's real-time capabilities - ideal for a hackathon demo.
One-Line Pitch
"Just like tracking a food delivery order, patients can track their OPD token in real time and walk in only when their turn is near."
Competitive Landscape & What Makes This Different
OPD queue and token management is not a new category - established products such as Cliniqwise, Ezovion, Webprint, NZCares, EMed HealthTech, and the Government of India's eHospital app already offer QR-based check-in, doctor-wise token queues, and SMS/WhatsApp status updates. This PRD does not claim to invent the category; it claims to execute a focused, real-time version of it within a hackathon timeframe, plus one feature none of the listed competitors currently offer.
All existing products tell the patient their queue position and an estimated wait time - and stop there.
None of them combine that with the patient's actual live location and real-time travel time to tell them exactly when to leave home. This system does, via the Smart Leave-Now Engine described in Section 7.9 - the project's signature, hardest-to-copy feature.
2. Problem Statement & Background
2.1 Current State
In a typical OPD setting today, the patient journey looks like this:
1. Patient arrives at the hospital and stands in a physical line at the reception counter.
2. Reception staff manually writes or prints a token number on paper.
3. The patient sits in a waiting area and listens for their number or name to be called aloud.
4. If the patient steps away (for a coffee, a phone call, to accompany a child to the washroom), they risk missing their turn.
5. Reception staff have no easy way to see how many patients are pending, how long each consultation is taking, or communicate delays.

Because the core requirement is real-time state synchronization across multiple simultaneous viewers (patient phones, reception dashboard, doctor dashboard, and a public waiting-room display), Firebase Firestore is an ideal fit: it is purpose-built for exactly this kind of live, multi-client data synchronization.

Token Generation Logic
Each doctor/department queue maintains a running counter for the current day. When a patient submits the check-in form, the system executes the following logic inside a Firestore transaction (to avoid two patients receiving the same token number if they check in at the exact same millisecond):
1. Read the current counter value for the selected doctor's queue document for today's date.
2. Increment the counter by 1 inside a Firestore transaction (guarantees atomicity even under concurrent writes).
3. Create a new document in the tokens sub-collection with the new token number, patient details, status = "waiting", and a server timestamp.
4. Return the token number and token ID to the Patient Flutter app, which stores it locally on-device (SharedPreferences) so the status screen re-opens directly on next app launch.
5. The app navigates automatically to the Live Status screen for that token, so the patient never has to note down or re-enter anything.
// Pseudocode - Token generation using a Firestore transactionasync function generateToken(doctorId, patientData) {  const counterRef = doc(db, `doctors/${doctorId}/counters/${todayDateKey}`);  return await runTransaction(db, async (tx) => {    const counterSnap = await tx.get(counterRef);    const current = counterSnap.exists() ? counterSnap.data().lastToken : 0;    const nextToken = current + 1;    tx.set(counterRef, { lastToken: nextToken }, { merge: true });    const tokenRef = doc(collection(db, `doctors/${doctorId}/tokens`));    tx.set(tokenRef, {      tokenNumber: nextToken,      ...patientData,      status: 'waiting',      createdAt: serverTimestamp()    });    return { tokenId: tokenRef.id, tokenNumber: nextToken };  });}
Using a transaction here is critical: without it, two patients checking in simultaneously could both read the same "last token = 14" value and both be assigned token 15, causing a collision. Firestore transactions guarantee that concurrent writes to the same counter document are serialized safely.
7.2 Feature: Live Queue Status (Patient View)
Once a token is generated, the Patient Flutter app subscribes to a real-time Firestore listener (via cloud_firestore's snapshots() stream) on their specific token document, as well as a query listener on the doctor's queue to calculate their live position.
What the Patient Sees
Their token number, large and prominent.
Current "Now Serving" token number for that doctor.
Number of patients ahead of them in the queue.
An estimated wait time (see calculation logic below).
A status badge: Waiting / You're Next / In Progress / Completed / Skipped.
Position & Estimated Wait Time Calculation
Position is calculated client-side (or via a Cloud Function for consistency) by counting how many tokens in the same doctor's queue have status = "waiting" and a token number lower than the patient's own token number.
// Position calculationposition = count( tokens where status == 'waiting'                   AND tokenNumber < myTokenNumber                   AND doctorId == myDoctorId )// Estimated wait timeavgConsultationTime = rollingAverage(last 10 completed consultations for this doctor)estimatedWaitMinutes = position * avgConsultationTime
The rolling average of the last 10 completed consultations (tracked via timestamps recorded when a doctor marks a token 'in-progress' and then 'completed') gives a realistic, self-adjusting estimate rather than a hardcoded fixed number per patient. This means the estimate automatically becomes more accurate as the day progresses and more real consultation data is collected.
Real-Time Sync Behaviour
The patient's screen requires zero manual refresh. This is achieved using Firestore's onSnapshot() listener, which pushes any change in the queue (a new token added, a token marked complete, a token skipped) to every subscribed client within milliseconds. This is the single most important demo moment: showing two screens side by side and calling 'Next' on one to instantly update the other.

Implementation Logic
Notifications are implemented using a Cloud Function triggered on Firestore document writes (onUpdate trigger on the tokens collection). Whenever a token's status or the queue's position count changes, the function checks whether a notification threshold has been crossed and, if so, sends a push notification via Firebase Cloud Messaging (FCM) to the patient's registered device token, delivered natively through firebase_messaging in the Flutter app. For the hackathon demo, if push permission is not granted on the device, the system falls back to a simple in-app banner on the Live Status screen, so the demo works reliably even without notification permissions.
exports.onTokenStatusChange = functions.firestore  .document('doctors/{doctorId}/tokens/{tokenId}')  .onUpdate(async (change, context) => {    const before = change.before.data();    const after = change.after.data();    if (before.status !== after.status) {      if (after.status === 'in-progress') {        await sendNotification(after.deviceToken, 'It is your turn now.');      }    }    // Recompute positions for all waiting patients in this doctor's queue    // and notify anyone whose position just became 3 or 1.  });

Roles are stored as a custom field (role: 'receptionist' | 'doctor' | 'admin') on a users collection document, and enforced both in the UI (hiding controls) and at the data layer via Firestore Security Rules, described in Section 11. 7.9 Signature Feature: Smart Leave-Now Engine (Reverse ETA Sync)
  This is the project's key differentiator. Existing OPD queue products (Cliniqwise, Ezovion, Webprint, NZCares, EMed HealthTech, and the Government eHospital app) all tell the patient their queue position and an estimated wait time. None of them tell the patient when to actually leave home. This feature closes that gap by combining the live queue ETA with a live, traffic-aware travel-time estimate.
Problem It Solves
A patient who checks in remotely still has to guess when to leave for the hospital. Leaving too early recreates the exact physical-waiting-room problem this whole system was built to remove. Leaving too late risks missing the call and being marked a no-show. The Smart Leave-Now Engine removes this guesswork entirely by sending a single, precisely-timed 'Leave Now' notification, calculated the same way a ride-hailing app times a 'your driver is arriving' alert.
How It Works - Step by Step
1. On the check-in screen, the patient sees an optional toggle: 'Notify me exactly when to leave.' This is off by default and requires explicit opt-in (privacy-first design).
2. If enabled, the Flutter Patient app requests one-time location permission and begins sending the patient's coordinates to Firestore at a low frequency (every 60-90 seconds) using the geolocator package - only while their token status is 'waiting'.
3. A Cloud Function (computeLeaveNow) is triggered on every location update and every queue-position change for that token.
4. The function calls the Google Maps Directions API with the patient's current coordinates and the hospital's fixed coordinates, requesting a traffic-aware driving/transit duration (travelTimeMinutes).
5. The function compares travelTimeMinutes against the patient's current estimatedWaitMinutes (calculated the same way as in Section 7.2, via the doctor's rolling average consultation time).
6. The moment travelTimeMinutes is greater than or equal to (estimatedWaitMinutes - a small safety buffer, e.g. 5 minutes), the function sends exactly one 'Leave Now' push notification via FCM and sets leaveNowSentAt so the same alert is never sent twice.
7. If the patient's queue position suddenly jumps forward (e.g., several patients ahead are marked no-show), the function recalculates immediately and can still fire the alert early, rather than waiting for the next scheduled check.
Logic Pseudocode
exports.computeLeaveNow = functions.firestore  .document('doctors/{doctorId}/tokens/{tokenId}')  .onUpdate(async (change, context) => {    const after = change.after.data();    // opt-in only, one-time alert    if (!after.travelTrackingEnabled || after.leaveNowSentAt) return;    if (after.status !== 'waiting' || !after.patientLocation) return;    // same estimation logic as Section 7.2    const estimatedWaitMinutes = await computeEstimatedWait(after);    const travelTimeMinutes = await getMapsTravelTime(      after.patientLocation, HOSPITAL_COORDS    );    const BUFFER_MINUTES = 5;    if (travelTimeMinutes >= (estimatedWaitMinutes - BUFFER_MINUTES)) {      await sendNotification(        after.deviceToken,        `Leave now - about a ${travelTimeMinutes} min ride, turn is close.`      );      await change.after.ref.update({        leaveNowSentAt: admin.firestore.FieldValue.serverTimestamp()      });    }  });
Why This Is Genuinely Hard to Copy Quickly
It requires wiring three live signals together (patient GPS, live traffic data, and live queue ETA) into a single recomputation loop - most competitor products only track one of these (queue ETA).
It needs a working rolling-average wait-time model (Section 7.2) as an input, so it only works well once the base queue system is already solid - it is a natural 'advanced feature to demo last' in the hackathon.
Because it degrades gracefully (patients who opt out just see the normal queue status), it adds a wow-factor demo moment without risking the core reliability of the app.
Privacy & Data Handling
Location sharing is strictly opt-in per visit, never enabled by default.
Location data is only stored on the token document for the duration of that single visit and is never shown to reception, doctors, or admins - it is used only by the Cloud Function for the travel-time calculation.
Location updates stop automatically the moment the token's status changes away from 'waiting' (called, completed, or skipped).
Demo Script for This Feature

Ours goes further - it knows how far you are from the hospital in real traffic, and tells you the exact moment to leave, the same way a cab app tells you when your ride is arriving. That's the one feature none of the existing hospital queue products on the market currently offer."

9.1 High-Level Architecture

9.4 Why Firebase Fits This Problem Well
Real-time by default: Firestore's onSnapshot() (identical in the Flutter SDK and the JS/React SDK) removes the need to build custom WebSocket/polling infrastructure.
One backend, three front ends: the cloud_firestore and firebase_auth Flutter packages and the Firebase JS SDK for React talk to the same collections, so business logic is written once.
No backend server to deploy or scale during the hackathon - Cloud Functions handle the few pieces of logic that must run server-side.
Built-in authentication with role support, shared across Flutter and React apps via the same users collection.
Generous free tier (Spark plan) is sufficient for a hackathon demo's expected traffic.
Firebase Hosting gives an instant, shareable HTTPS demo URL for the React Admin/Reception panel; Flutter apps can be run via emulator or a debug APK link for judges.

users (collection)  └── {uid} (document)  -- matches Firebase Auth UID        name: string        role: string          'receptionist' | 'doctor' | 'admin'        doctorId: string      (only present if role == 'doctor')        createdAt: timestamp
10.4 Collection: dailyStats (for Admin Analytics)
dailyStats (collection)  └── {doctorId}_{dateKey} (document)        totalServed: number        totalSkipped: number        avgWaitMinutes: number        avgConsultationMinutes: number        peakHour: number  (0-23)
This document is updated incrementally by a Cloud Function every time a token's status changes to 'completed' or 'skipped', rather than being computed on-demand by scanning the full tokens collection. This keeps the Admin Analytics dashboard fast even as the number of tokens grows.

11. Firestore Security Rules
Security rules are the actual enforcement layer - they run on Firebase's servers and cannot be bypassed by a modified client, unlike UI-level restrictions. Below is the rule set for this system.
rules_version = '2';service cloud.firestore {  match /databases/{database}/documents {    function isSignedIn() { return request.auth != null; }    function getRole() {      return get(/databases/$(database)/documents/users/$(request.auth.uid)).data.role;    }    match /doctors/{doctorId} {      allow read: if true; // public can view doctor list + queuePaused status      allow write: if isSignedIn() && getRole() == 'admin';      match /tokens/{tokenId} {        allow read: if true; // patients + public display need read access        allow create: if true; // patient self check-in, no auth required        allow update: if isSignedIn() &&                         (getRole() == 'receptionist' || getRole() == 'doctor');        allow delete: if isSignedIn() && getRole() == 'admin';      }      match /counters/{dateKey} {        allow read: if true;        allow write: if true; // guarded by transaction logic, not by auth      }    }    match /users/{userId} {      allow read: if isSignedIn() && request.auth.uid == userId;      allow write: if isSignedIn() && getRole() == 'admin';    }    match /dailyStats/{statId} {      allow read: if isSignedIn() && getRole() == 'admin';      allow write: if false; // only Cloud Functions (admin SDK) can write    }  }}
Note on token creation being unauthenticated: this is an intentional product decision to keep patient check-in frictionless (no account required). The trade-off is documented here so it can be explained confidently to judges - abuse risk is low in a hackathon demo context, and a production version would add App Check or rate-limiting via Cloud Functions to prevent spam token creation.

14. Edge Cases & Error Handling
Scenario
Handling Strategy
Two patients check in at the exact same moment
Firestore transaction on the counter document guarantees sequential, non-duplicate token numbers.
Patient uninstalls/reinstalls the app or switches devices
Reception can look up the patient by phone number on the Admin panel and re-display or reissue the token status.
Doctor calls 'Next' but queue is empty
UI shows 'No patients waiting' and disables the button until a new token is created.
Patient never shows up when called
Doctor or reception marks token as 'Skipped' after a configurable grace period (e.g., 3 minutes), and the queue auto-advances.
Network disconnects on a patient's phone mid-session
Firestore's offline persistence caches the last known state locally and auto-syncs once connectivity returns.
A doctor's queue needs to be paused (emergency, break)
queuePaused flag halts new 'Call Next' actions; all patient screens display a delay banner rather than a false ETA.
Push notification permission denied on patient's device
System falls back to an in-app banner on the Live Status screen; patient can still see live status any time they open the app.
Receptionist accidentally adds a patient to the wrong doctor
Reception dashboard supports a 'Reassign Doctor' action that transfers the token to a new queue with a fresh token number.
Midnight rollover while patients are still waiting
resetDailyQueue Cloud Function only archives tokens with status 'completed' or 'skipped'; any still-waiting tokens are carried over rather than deleted.

16. Development Roadmap (Hackathon Timeline)
The build is sequenced so that a working, demoable core (check-in → live status → call next) exists as early as possible, with polish and secondary features layered on afterward. This is important in a hackathon: a simple working demo beats an ambitious broken one.

19.2 Explaining This Project to Judges - Suggested Script
"Hospitals still manage OPD queues with paper tokens and physical lines. Our system lets a patient check in from their phone, see their live position and estimated wait time - just like tracking a food delivery - and walk in only when their turn is close. On the backend, we use Firebase Firestore's real-time database so that the moment a doctor clicks 'Next Patient', every connected screen - the patient's phone, the reception dashboard, and the waiting-room display - updates instantly with zero refresh. We used Firebase specifically because it gave us real-time sync, authentication, and hosting without needing to build or deploy a custom backend server, which let us focus our hackathon time on the actual user experience."
19.3 References for Data Model Decisions
Firestore was chosen over a relational database because the core requirement - many simultaneous clients needing live, low-latency updates to a shared queue state - is precisely the use case Firestore's snapshot listeners are designed for. A traditional SQL database would have required a separately built WebSocket or polling layer to achieve the same real-time effect.
